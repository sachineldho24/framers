  - **Custom page size** (`DOCUMENT_VERSION` 5, `doc.printMm`) — Resize menu → "Custom size…" → `CustomSizeDialog`. Width/height in **px · mm · cm · in**, an aspect-ratio link-lock, recent sizes (per-browser, `localStorage` key `framers.studio.recentSizes`), and a "Scale artwork to fit" reflow toggle. The pure core is `src/lib/studio/customSize.ts` (`MIN_SIZE_MM = 20`, `MAX_SIZE_MM = 1500`, `MAX_RECENT_SIZES = 6`).
    - **A page has a physical size and the pixel grid is derived from it — never the other way round.** `docSizeForFrame` caps the long edge, so a 4096 px page is A2 at 175 DPI *or* A4 at 300 depending on a fact that pixels alone can't carry. Hence `printMm` on the document: present, it *wins* over the session's frame in `StudioContext`, so the lip guides, the DPI readout, `LayerInfoSheet`, `BorderPanel`, `TextPanel` and the PDF's `/MediaBox` all follow one number. Hence also that **px input is physical**: pixels are read at `PRINT_DPI`, converted to mm, then run the same path as mm/cm/in — typing 2480 × 3508 px gives A4. `migrateDocument` coerces `printMm` and silently drops a non-positive or malformed one (falling back to the frame beats quoting nonsense).
    - `resizeDocument` takes `printMm?: {…} | null` — **omitted keeps** what's there (a later reflow must not lose the paper), **`null` clears** it, handing authority back to the frame row. The no-op short-circuit compares pixels *and* paper, since the same grid at a different paper size is a real change.

  - **Aspect presets** (crop bar: Frame · 1:1 · 3:4 · 4:5 · 5:7 · 2:3, turned to match the page). One action, `setLayerAspect`, because of the renderer's crop contract: `drawImage` stretches the cropped source into the whole layer box, so the shape the viewer sees is the **box's** and the shape of the pixels is the **crop's** — set either alone and the photo is distorted by exactly the difference. `fitToAspect` (in `crop.ts`, pure) returns both: the box keeps its area and centre but is capped to the page, and the crop is the largest rect of the matching *source* shape (natural size folded in) inside the crop the user already has, so their zoom survives and it can only narrow. The lit button is `aspectMatches` read back off the layer, **not a stored mode**, so a free handle drag afterwards un-lights it rather than lying.
  - **Snapping + smart guides** (`snap.ts`, pure; `SnapGuides.tsx` at `z-[6]`, between `PrintGuides`' `z-[5]` and the selection chrome). Applied in the `move` branch only, and only to **unrotated** boxes — `x/y/width/height` describe the unrotated box, so a turned layer's stored edges are not the edges anyone can see. Candidates in priority order (earlier wins a tie): page centre → page edges → **safe box** → other layers' edges and centres; hidden and rotated neighbours are skipped, as is the dragged layer itself. The safe rect is a target because that is where the moulding stops covering the artwork — the paper's edge would put a caption under the lip; it is only offered while the guides are actually visible. `SNAP_TOLERANCE = 6` is **screen** px, divided by `viewport.scale` at the call site so the pull feels identical at every zoom. The nudge is added *after* the per-pixel rounding, so the edge lands exactly on the line being drawn. **Alt** bypasses it (Ctrl/⌘ is wheel-zoom, Shift is the aspect locks). Line sets are diffed through `snapKey` so dragging along a snapped edge doesn't re-render the overlay every move.
  - **Pinch zoom/pan** — a `pointersRef` map plus a `pinch` `Gesture`. The second `pointerdown` calls `endGesture()` first, so a half-finished layer move lands as its own undo step, then takes the viewport until fewer than two pointers remain (lifting one of two must not end the gesture, or the view jumps). Every move recomputes from `startViewport`/`startDistance`/`startMid` rather than accumulating — a wandering pinch can't drift the page off the fingers — via `zoomBy(startViewport, dist/startDistance, startMid)` then an offset by the midpoint's travel, so one gesture both zooms and pans with no mode.
  - Never stores pixels: erase/restore are **replayed normalised polylines**, crop is a normalised source rect. Document JSON stays small and undo stays exact.
  - Canvas draws artwork only; selection box, handles, crop overlay and both floating toolbars are **DOM** positioned by the viewport transform — so cursors, hover, tooltips and focus work natively.
  - **Handle contract — read before adding any grab handle.** The overlays are *siblings* of `<canvas>`, not children, so a `pointerdown` on a handle never reaches `StudioCanvas.onPointerDown` and the canvas's `hitTestTargets` branch can't see it. `SelectionOverlay`/`CropOverlay` therefore take `onHandleDown`/`onHandleMove`/`onHandleUp` from the canvas (`beginHandleGesture`, `beginCropHandleGesture`) and each handle calls `setPointerCapture` **on itself**, so the rest of the drag is delivered to the handle wherever the pointer goes. `finishGesture` releases capture on `e.currentTarget`, not on the canvas. A new handle that only sets `pointer-events-auto` and a cursor will render correctly and do nothing.
  - **Viewport centring.** `StudioContext` carries a `viewportPristineRef` — set by `fitTo`, cleared by every other viewport write. A `ResizeObserver` on the canvas wrap re-fits while the viewport is pristine (so the first measurement being taken before the chrome settles is self-correcting) and otherwise shifts the offset by half the size delta, keeping the page centred as a flyout opens or closes without re-zooming work in progress. Do not reintroduce a one-shot `fitted` latch.

Reconciliation lives in an unconditional `try/finally`; safe because every setter reads the current ref and the cache is keyed by storage path.

A 401 from `flatten` is reported as a lapsed sign-in, since the fix differs from a network failure — nothing is lost either way, the document is saved and pressing Done again is the whole recovery.

## Canva Integration Reality

The Canva Connect API **cannot embed the editor in an iframe**. The flow is always a redirect:

1. App calls `POST /rest/v1/designs` to create a design with preset dimensions
2. App redirects the user to `https://www.canva.com/design/{designId}/edit`
3. User designs in Canva, then returns to the app
4. App calls `POST /rest/v1/exports` to export the design, then polls `GET /rest/v1/exports/{exportId}`

Public integrations require Canva review/approval before non-developer users can authenticate. This is a launch blocker — see `plan/08-open-questions.md` once it exists.

**Return navigation** brings the user back after designing: the editor URL carries `correlation_state` (the **session id**, `withCorrelationState`); Canva's "Return to Framers" button hits `GET /api/canva/return?correlation_jwt=...`; that route verifies the JWT (jose, against `CANVA_JWKS_URL`, audience = client id, `type === "rti"`), then lands on `/design/{sessionId}/review`. The button only renders when the design is opened via Canva's **token-based `edit_url`** (fetched live via `getDesign`, valid ~30 days) — a plain `/design/{id}/edit` URL shows no button. Requires the **Return URL** set in the Developer Portal (`/api/canva/return`).

**Post-OAuth flow:** callback stores tokens + creates the design, then redirects to the **`/design/[sessionId]/open` interstitial** (NOT straight into the editor — avoids the fresh-signup "design is private" 403). The user clicks "Open in Canva" there. Export is **split start/poll** (`/api/canva/export/start` → `/api/canva/export/status`), not a single long-poll, to stay under Vercel's 60s cap.

## Key Business Rules

- Admin role is determined by `app_metadata.role = 'admin'` in Supabase Auth (NOT `user_metadata`, which users can edit themselves — security fix vs. the original plan). Set it via SQL with the service role: `UPDATE auth.users SET raw_app_meta_data = raw_app_meta_data || '{"role":"admin"}'::jsonb WHERE email = '...'`. Check it only via `isAdmin()` in `src/lib/auth.ts` or `public.is_admin()` in SQL/RLS.
- All prices in INR (paise for Razorpay)
- Razorpay webhook signature must be verified server-side before creating any order record
- **Checkout/payment flow (Phase 4, built):** pending-order pattern. `POST /api/payments/create-order` reads the price from the DB (never trusts the client), creates a Razorpay order + a `payment_status='created'` order row, returns `{keyId, razorpayOrderId, amountPaise, orderId}`. Browser opens Razorpay Checkout (`src/lib/razorpay-client.ts`). On success → `POST /api/payments/verify` (HMAC of `order_id|payment_id`) flips the row to `paid`; the webhook (`/api/payments/webhook`, HMAC of raw body) does the same independently — both idempotent, webhook is source of truth. Requires migration `0005_pending_orders.sql` (nullable `razorpay_payment_id`, `payment_status` default `created` + states created/paid/failed/refunded) and `RAZORPAY_WEBHOOK_SECRET`. Register the webhook URL in the Razorpay dashboard pointing at `/api/payments/webhook` (events: `payment.captured`, `order.paid`).
- Canva OAuth tokens per user are stored in a `canva_tokens` table; refresh logic must handle expiry
